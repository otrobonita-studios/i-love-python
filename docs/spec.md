## 0. Non-negotiable constraint: pure Python

Every line of source the project *author* writes is Python. This is a hard rule, not a slogan, and it's enforced two ways:

1. **CI check.** A `scripts/lang_audit.py` step scans the repo tree (excluding `vendor/`, `node_modules`-equivalents, and anything under a `generated/` marker) and fails the build if any non-`.py` source file (`.js`, `.ts`, `.sh` written by hand, etc.) is committed outside an explicitly whitelisted `generated/` directory.
2. **The escape hatch is explicit, not silent.** Where the app needs a non-Python tool (k6 below), the tool's native script is *generated by Python at build time* into `generated/`, never hand-authored, never committed as source-of-truth. The human — and any coding agent working on the repo — never opens an editor on a `.js` file. This distinction ("Python writes the artifact, Python owns the artifact") is the load-bearing idea that lets the pure-Python claim survive contact with real tooling.

Framework choice for the UI: a pure-Python web framework (Reflex or NiceGUI, decide in prototyping — both compile Python to a browser UI without hand-written JS/HTML being part of the source tree) rather than FastAPI+Jinja2+hand-written JS, so the "written only in Python" claim holds all the way to the DOM, not just the backend.

## 1. Landing page — "I ❤️ PY"

The Glaser parody, but the artifact is generated, not designed:

- A Python module (`art/heart.py`) renders the heart procedurally — parametric heart curve (`x = 16sin³t`, `y = 13cos t − 5cos 2t − 2cos 3t − cos 4t`), not a traced SVG. Rendered server-side to SVG with `svgwrite` or client-side live via Pyodide so a visitor can watch it draw.
- Typography: serif caps, "I", generated heart, "PY" — matching the original's proportions closely enough to read as the reference without reproducing it pixel-for-pixel (see below on trademark caution).
- A one-line caption under the mark: *"Rendered by the code you're about to inspect."* — sets the premise for the rest of the site immediately.
- **Caution flag for you, not a build task:** the original I ❤️ NY mark is a registered trademark (NYS Dept. of Economic Development). A parody/homage is broadly defensible territory but worth a beat of thought before this becomes a public-facing asset with your name on it — flagging it here rather than deciding it for you.

## 2. Quality telemetry panel (Observable-21 lineage)

Visually: same panel language as Observable 21's Langfuse-style sidebar, but every reading is real, not `SIMULATED`. This is the module that answers "how do I show quality without being able to read the code myself" — the tools read it, the panel renders their verdicts.

| Signal | Tool | Rendered as |
|---|---|---|
| Formatting | `ruff format --check`, `black --check` | pass/fail badge, 0 deviations |
| Type safety | `mypy --strict` | error count, trending to 0 |
| Test coverage | `pytest` + `coverage.py` | animated heatmap over the file tree |
| Complexity | `radon cc` / `radon mi` | per-module radar chart |
| Security | `bandit` | findings list, tied thematically to your leaked-API-key incident from Observable 21's security rung — same story, different repo |
| Dependency health | `pip-audit` | CVE badge |

Footer line, matching Observable 21's honesty convention: *"live tool output · not a taste opinion."*

## 3. Multi-persona code review

Three reviewer personas, same pattern as Observable 21's conservative/aggressive/analytical table:

- **The Purist** — readability, naming, PEP 8 spirit beyond what `ruff` catches mechanically
- **The Skeptic** — security and failure-mode focus, "what breaks this at 3am"
- **The Pragmatist** — performance and complexity, "is this over-engineered for what it does"

On a real diff, each persona posts a short verdict in plain language before the raw diff is shown — so the *argument* is legible before the *syntax* is. Example exchange style (for the agent building this — tone reference, not literal copy):

> **Skeptic:** This subprocess call passes an unsanitised path straight to k6's config loader. Flag it before merge.
> **Purist:** Naming's fine, but `generated/` needs a `.gitattributes` marker so diffs against it don't spam reviewers.
> **Pragmatist:** Complexity's fine at this size — no over-abstraction yet.

Verdicts land in a changelog panel; the raw diff is one click away for anyone who *does* want to read Python.

## 4. Git discipline module

Direct showcase of the playbook's core claim: agents use git as a queryable interface, not an archive, so commit granularity is a functional requirement.

- A live "ask git" console: an agent runs `git log`, `git blame`, `git bisect` on stage against a real bug, narrating its reasoning from commit messages alone.
- Commit timeline rendered as a strip of atomic, small commits with clean messages — visually contrasted (toggle) against a synthetic "bad" history of squashed, vague commits, to make the functional cost of poor discipline legible rather than asserted.
- Each commit's trailer references its `intent.md`/`MANIFEST.md` entry where relevant — surfacing your home-made manifest convention as a first-class artifact in the UI, not a hidden file.

## 6. Integration + complexity proof: k6 load simulation

This is the module that shows Python orchestrating *outside* its own runtime, honestly:

- `loadtest/spec.py` — a Python dataclass describing the scenario (endpoint, VUs, ramp profile, duration, thresholds).
- `loadtest/generate.py` — compiles that dataclass into a k6 JS script under `generated/k6/scenario.js`. This file is git-ignored from "source" status (tracked as a build artifact, clearly labelled at the top: `// GENERATED — do not edit, edit loadtest/spec.py instead`).
- CI runs `k6 run generated/k6/scenario.js --out json=results.json` against a staging instance of the quality-telemetry API from module 2.
- A Python module (`loadtest/report.py`) parses the k6 JSON output and renders it into the same Observable-21-style panel: p95 latency, error rate, VU ramp, rendered as a live chart — same "best-effort telemetry, not a game record" honesty footer.
- Narrative purpose: it demonstrates that "pure Python" doesn't mean "isolated from the rest of the toolchain" — it means Python stays the single source of truth even when it delegates execution to something else. That's the more sophisticated and more honest claim than "no other tools involved."

### Tests that demonstrate complexity, not just coverage

Coverage percentage is a weak complexity signal on its own, so pair it with:

- **Property-based tests** (`hypothesis`) on the core `art/heart.py` curve generator and the `loadtest/spec.py` → k6-JS compiler — both are good hypothesis targets because they're pure transforms with clear invariants (e.g. "compiled script always contains the configured VU count").
- **Mutation testing** (`mutmut` or `cosmic-ray`) run as a scheduled (not per-PR, too slow) job, with the mutation-survival score shown on the quality panel as a second-order trust signal beyond raw coverage.
- **Contract test** for the k6 integration itself: assert the generated JS is syntactically valid (shell out to `k6 inspect` or a JS parser) *before* a real load test ever runs — catching a broken generator without burning a full load-test cycle.
- **Integration test** for the full loop: spec → generate → run (against a local mock server, short duration) → parse → panel data — proving the whole chain end-to-end, not just each unit.
